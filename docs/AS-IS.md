## 대상 (가상 페르소나)
- 개인 셀러. 하나의 판매 채널에서 수공예품·식품 같은 소량 상품을 판다.
- 가정: 판매자(셀러)가 여러 명 모인 소규모 마켓이고, 인기 상품은 한정 수량으로 선착순 판매한다.
- 가정: 운영자 1명이 셀러들의 정산을 맡는다. (수치는 설계용 가정이며 실제 통계가 아님)

## 현재 흐름 (엑셀과 수작업)
1. **주문 접수**: 채널별 주문 목록을 내려받아 엑셀 한 장에 모은다.
2. **결제 확인**: 결제 대행사(PG) 정산 내역과 주문 목록을 눈으로 대조한다.
3. **재고 관리**: 엑셀 재고표를 직접 수정한다. 주문이 몰리면 수량 갱신이 늦어진다.
4. **환불·취소**: 환불이 생기면 원 주문 행을 찾아 정산표를 수동으로 고친다. 환불이 정산 시점보다 늦게 오면 이미 보낸 정산을 다시 건드려야 한다.
5. **정산**: 기간별로 매출 − 환불 − 수수료를 계산해 셀러별 금액을 만들고 입금한다.

## 문제점
| 문제 | 영향 | 근거 |
| --- | --- | --- |
| 정산 금액이 기대와 달라 원인 추적이 어렵다 (미정산, 차감액 차이, 중복 정산 등) | 대조에 시간이 들고 오류가 반복된다 | 자료 1, 3, 4 |
| 환불이 원 매출과 다른 시점에 반영되어 정산이 꼬인다 | 이미 확정한 정산을 수정해야 한다 | 자료 1, 3 |
| 수수료·공제 항목이 채널마다 달라 매출과 입금액이 안 맞는다 | 월말 정산 때 차액 확인에 시간이 든다 | 자료 1, 4 |
| 수기 재고 관리로는 한정 수량 상품에서 초과 판매가 난다 | 취소·사과 처리, 신뢰 하락 | 자료 2 |
| 할인·선착순처럼 짧은 시간에 주문이 몰릴 때 재고가 실시간으로 안 맞는다 | 마지막 수량에서 동시에 여러 주문이 성립 | 자료 2 |
| 정산 대조를 월 단위로 몰아서 하면 문제 하나가 커진다 | 오류 원인 범위가 넓어진다 | 자료 3, 4 |

## 개발자 관점의 AS-IS (본인 프로젝트 경험)
techconf(IT 컨퍼런스 예약 플랫폼)에서 결제·정산·환불과 동시 신청을 구현하며 확인한 것이다.
- 결제와 환불 상태, 정산 금액이 서로 어긋나지 않게 하려면 **금액 정합성을 검증하는 쿼리와 테스트가 필수**였다.
- 동시 신청이 몰리면 **재고(정원) 정합성과 응답 시간**이 함께 문제가 되었고, 부하 테스트(k6)에서 지연이 크게 늘었다.
- 같은 요청이 두 번 들어와도 결과가 한 번과 같아야 하는 **멱등성** 문제가 생겼다.

## 자동화 후보 (TO-BE 문서로 이어짐)
- 일 정산 배치로 셀러별 정산을 자동 계산하고, 중복 실행에도 결과가 같게 만든다.
- 환불은 "환불이 일어난 날"의 정산에서 차감해 이미 확정한 정산을 고치지 않는다.
- 선착순 상품의 재고를 서버가 원본으로 관리해 초과 판매를 막는다.
- 정산 완료를 셀러에게 알린다. (n8n 또는 Apps Script)
