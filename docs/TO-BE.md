# TO-BE: market-settlement 도입 후 흐름

AS-IS([docs/AS-IS.md](AS-IS.md))의 문제를 서비스가 어떻게 바꾸는지 정리한다.

## 흐름 비교
| 단계 | AS-IS (엑셀·수작업) | TO-BE (이 서비스) |
| --- | --- | --- |
| 주문 접수 | 목록을 모아 엑셀에 붙여 넣음 | 주문 API가 `orders`, `order_item`에 즉시 기록 |
| 결제 확인 | PG 내역과 주문을 눈으로 대조 | PortOne 결제 검증 후 상태 `PAID`, 멱등성 키로 중복 방지 |
| 재고 | 엑셀 재고표를 수정 | `inventory`가 원본. 선착순 상품은 Redis로 선점 후 DB 확정 |
| 환불 | 원 주문을 찾아 정산표를 수동 수정 | 환불 기록 후 **환불이 일어난 날**의 정산에서 차감 |
| 정산 | 월말에 수동 계산 | 일 정산 배치가 판매자별로 자동 계산, 재실행해도 중복 없음 |
| 검증 | 사람이 합계를 확인 | 정합성 쿼리가 매일 `결제 − 환불 = 정산 net + 수수료`를 확인 |
| 알림 | 직접 연락 | 정산 완료 알림 자동화 (n8n 또는 Apps Script) |

## 문제별 해결 방식
| AS-IS 문제 | 해결 | 구현 위치 |
| --- | --- | --- |
| 정산 금액 불일치 | 정산 항목을 원천 건(주문 항목, 환불) 단위로 저장하고 유니크 제약으로 중복 방지 | `settlement_item`, #13, #14 |
| 환불 시점 불일치 | 확정된 정산을 수정하지 않고 환불일 정산에서 차감 | docs/ERD.md 설계 결정, #9, #13 |
| 수수료 차이 | 판매자별 `fee_rate`를 정산 시점 값으로 고정 저장 | `settlement.fee_rate` |
| 초과 판매 | Redis 재고 선점 + DB `CHECK (stock >= 0)` | #11 |
| 주문 집중 시 지연 | 조회 캐시, 요청 제한, k6로 전후 측정 | #10, #12, #23, #24 |
| 월 단위 몰아서 대조 | 일 단위 정산과 자동 검증 | #13, #14 |

## 성공 기준 (PRD 연결)
- 초과 판매 0건 (1,000 동시 요청 k6)
- 정산 정합성 오류 0건
- 정산 배치 재실행 시 결과 동일
- 개선 전후 p95를 `docs/performance.md`에 기록
