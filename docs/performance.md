# 성능 측정

개선 전(기준) 수치를 먼저 기록하고, 개선 후 수치를 같은 시나리오로 다시 재서 비교한다. 모든 수치는 아래 "측정 환경"의 한 대 PC에서 잰 것이다.

## 요약
| 시나리오 | 지표 | 개선 전 | 개선 후 | 한 일 |
| --- | --- | --- | --- | --- |
| 상품 조회 (50명, 30초) | 응답 p95 | 18.0ms | 11.4ms (-37%) | Redis 캐시 (#10) |
| 선착순 구매 (1,000건 요청) | DB 트랜잭션 수 | 857~1,416 | 76~78 | Redis 재고 선점 (#11) |
| 정산 (정산 2,900건) | 정합성 검증 시간 | 101초 | 0.18초 | 검증 쿼리 개선 (#55) |
| 정산 (판매자 100명, 하루) | 정산 시간 | 1.8초 | 1.13초 | 인덱스와 일괄 조회 (#55) |

- 선착순에서 초과 판매는 개선 전후 모두 0건이다. 정산 결과는 개선 전후 해시가 같다.
- 개선 폭은 시나리오마다 다르다. 응답 시간이 거의 안 변한 곳(선착순 p95)도 있고, 그 이유는 각 절에 적었다.
- 한계와 해석 주의는 맨 아래 "한계"에 모았다.

## 측정 환경
- 한 대의 PC에서 앱, PostgreSQL, k6를 모두 실행 (Windows 11, Docker Desktop, 12 CPU, 16GB)
- 앱: Spring Boot 4, Java 21, Tomcat·HikariCP 기본 설정 (커넥션 풀 10개)
- DB: PostgreSQL 17 기본 설정, 시드 데이터 (`scripts/seed.sql`): 판매자 100명, 상품 2,000개, 주문 10만 건, 주문 항목 약 20만 건, 환불 약 1만 건
- 같은 PC에서 부하 도구가 CPU를 나눠 쓰므로 절대값보다 전후 비교로 본다.

## 재현 방법
```bash
RATE_LIMIT_ORDER=100000 RATE_LIMIT_LOGIN=100000 docker compose up -d --build   # 요청 제한(주문 5회/10초, 로그인 10회/분)을 올려서 측정
docker compose exec -T postgres psql -U market -d market -v ON_ERROR_STOP=1 < scripts/seed.sql
k6 run perf/product-read.js
k6 run -e FLASH_PRODUCT_ID=<id> perf/flash-sale.js          # 사전: 해당 상품 재고를 100으로
k6 run -e FLASH_PRODUCT_ID=<id> -e MODE=spread perf/flash-sale.js
k6 run perf/settlement.js                                     # 사전: settlement 테이블 비우기
```

## 측정 결과 (개선 전 → 후)

### 1. 상품 조회
50명이 30초 동안 목록(80%, 0~99페이지 무작위)과 상세(20%)를 요청. 각 3회 측정.

| 구분 | 지표 | 캐시 전 | 캐시 후 (#10) | 변화 |
| --- | --- | --- | --- | --- |
| 전체 | p95 | 18.0ms | 11.4ms | -37% |
| 전체 | 평균 | 9.0ms | 7.2ms | -20% |
| 목록 | p95 | 18.2ms | 11.7ms | -36% |
| 상세 | p95 | 17.0ms | 8.7ms | -49% |
| 처리량 | 초당 요청 | 약 5,400 | 약 6,900 | +27% |

실패는 둘 다 0건이고 3회 측정이 거의 같다.
- 상품이 2,000개라 DB 조회가 이미 빨라서 개선 폭은 크지 않다. 같은 PC에서 k6와 앱이 CPU를 나눠 쓰는 점도 있다. 데이터가 많거나 쿼리가 무거울수록 캐시 효과가 커진다.
- 캐시 TTL은 30초다. 재고(stock)가 포함된 응답이라 주문이 들어와도 최대 30초 동안은 옛 재고가 보일 수 있다. 주문 처리는 DB 조건부 UPDATE로 하므로 판매 정합성에는 영향이 없다.
- Redis를 꺼도 조회는 DB로 계속된다. 연결 대기가 기본값이면 요청이 한참 멈춰서 타임아웃을 200ms로 줄였고, 꺼진 동안 요청당 약 0.4초가 추가된다(켜면 바로 정상).

### 2. 선착순 구매
재고 100개인 상품에 1,000건의 주문(1개씩)을 요청.

| 방식 | 주문 성공 | 재고 부족(409) | 연결 실패 | 응답 p95 | 초과 판매 |
| --- | --- | --- | --- | --- | --- |
| 한꺼번에 1,000명 (burst) | 100 | 113~237 | 663~787 | 305~554ms | 0건 |
| 2초에 걸쳐 1,000건 (spread) | 100 | 900 | 0 | 60ms | 0건 |

- 어느 방식이든 주문 항목 100건, 재고 0으로 초과 판매는 없다. 조건부 UPDATE(`stock >= qty`)가 막는다.
- burst에서는 요청 대부분이 서버에 닿기 전에 연결 거부로 실패한다. 서버 로직이 아니라 접속 단계의 문제이고, 원인은 아래 "burst 연결 거부 원인 확인"에서 가렸다.
- 이 앱은 모든 요청이 DB 재고 갱신(행 잠금)을 거친다. Redis 선점(#11)으로 재고 부족 요청을 DB에 보내지 않는 것이 개선 방향이다.

**Redis 선점 후 (#11)** — 같은 시나리오, 선착순 상품(`flash_sale`)만 적용. 선점을 끈 쪽은 같은 상품의 `flash_sale`를 false로 바꿔 비교했다.

| 방식 | 지표 | 선점 없음 | 선점 있음 |
| --- | --- | --- | --- |
| spread | DB 트랜잭션 수 (1,000건 요청, 3회) | 857, 1,108, 1,416 | 76, 77, 78 |
| spread | 응답 p95 | 47~58ms | 58~61ms |
| spread | 응답 중앙값 | 2.6~3.3ms | 2.1~2.6ms |
| burst | 주문 성공 / 초과 판매 | 100 / 0건 | 100 / 0건 |

- DB 트랜잭션이 약 10~18배 줄었다. 재고 부족 900건이 DB에 닿지 않고 Redis에서 거절된다. 남은 70여 건은 성공한 주문 100건 중 일부와 로그인 등이다(측정 중 같은 DB 전체 트랜잭션 수라 로그인 50건 등이 섞여 있음).
- 응답 시간은 거의 같다. 이 규모(초당 500건, 한 대)에서는 DB의 조건부 UPDATE가 이미 빨라서 지연이 병목이 아니었다. 이득은 응답 속도보다 DB 부하와 커넥션 사용량이다. p95는 성공한 주문 100건(전체의 10%)의 처리 시간이 정한다.
- burst의 연결 거부는 그대로다. 서버 로직 이전의 접속 단계 문제라서 선점으로는 해결되지 않는다.

#### burst 연결 거부 원인 확인
burst에서 연결이 거부되는 원인을 두 가지로 나눠서 같은 시나리오(재고 100, 1,000명 동시, 선점 없음)로 각 3회 확인했다.

| 조건 | 주문 성공 | 재고 부족(409) | 연결 실패 | 초과 판매 |
| --- | --- | --- | --- | --- |
| 기본 설정, PC에서 k6 실행 | 100 | 187~287 | 613~713 | 0건 |
| Tomcat `accept-count` 2000 | 100 | 124~277 | 623~776 | 0건 |
| k6를 compose 네트워크 안에서 실행 | 100 | 900 | **0** | 0건 |

- 대기열(`accept-count`)을 20배로 늘려도 연결 실패는 줄지 않았다. 원인이 Tomcat 접속 대기열이 아니라서 설정은 바꾸지 않았다.
- k6를 같은 compose 네트워크 안의 컨테이너로 돌리면(PC의 포트 전달을 거치지 않음) 연결 실패가 0건이고 모든 요청이 서버에 닿는다. 연결 거부는 PC에서 Docker Desktop의 포트 전달 계층으로 들어오는 구간에서 생긴다. 서버가 아니라 측정 환경의 한계다.
- 그래서 burst의 응답 시간(p95 약 400~480ms)은 연결 실패 없이 잰 값으로 본다. 요청 1,000건이 한꺼번에 서버에 닿으면 DB 행 잠금에 줄을 서서 spread(60ms)보다 느려진다.

```bash
# compose 네트워크 안에서 k6 실행 (포트 전달을 거치지 않는다)
docker run --rm --network market-settlement_default -v "$PWD/perf:/perf" grafana/k6 run -e BASE_URL=http://app:8080 -e FLASH_PRODUCT_ID=<id> /perf/flash-sale.js
```
주의: 선착순 상품은 `status`가 ON_SALE이어야 한다. 숨김 상품이면 모든 주문이 404로 실패한다(측정 중 한 번 겪음).

### 3. 정산 배치
최근 30일을 하루씩 정산(하루 주문 약 3,300건, 항목 약 6,700개). 정산 2,900건과 명세 205,432건 생성.

| 항목 | 기준 | 인덱스만 추가 | 인덱스 + 쿼리 개선 |
| --- | --- | --- | --- |
| 하루 정산 (판매자 100명) 평균 | 1.8초 (1.6~2.4) | 1.44초 | **1.13초** (0.8~1.5) |
| 29일 합계 | 약 52초 | 약 42초 | 약 33초 |
| 정합성 검증 (정산 2,900건 전체) | 101초 | 114초 | **0.18초** |

정산 결과(정산 2,900건의 금액 6개 열)의 해시가 기준 측정과 개선 후 측정에서 같다. 불일치는 모두 0건.

- `order_item(order_id)` 인덱스는 정산을 약 20% 줄였지만 정합성 검증은 줄이지 못했다. 검증의 병목은 인덱스가 아니라 정산 행마다 판매자의 항목 전체를 훑는 구조였다.
- 정합성 검증을 (판매자, 날짜)별 합계를 한 번만 만들어 붙이는 쿼리로 바꿔서 101초가 0.18초로 줄었다. 대신 검증 때 결제 전체를 한 번 훑으므로, 데이터가 쌓이면 시간이 늘어난다(날짜 범위로 좁히는 것은 개선 후보).
- 정산은 판매자마다 보내던 쿼리 3개(판매, 환불, 수수료율, 하루 약 300번)를 하루 3번으로 줄였다. 쓰기(정산 행과 명세 삽입)는 그대로 판매자별 트랜잭션이라 시간이 절반까지는 줄지 않았다.
- 기준 측정에서 하루 정산이 늘다가 줄었던 원인은 확인하지 못했다. 날짜별 결제 건수는 하루 3,400건 안팎으로 일정해서 데이터 양 때문은 아니다. 개선 후 측정에서는 날짜 전체가 1.1~1.2초로 평평했고, 기준 측정 직전 대량 삭제 뒤 DB 통계와 정리가 덜 된 영향으로 추정한다.

## 한계
- **환경**: 앱, DB, Redis, k6가 한 대의 PC에서 같이 돈다. 부하 도구가 CPU를 나눠 쓰고 Docker Desktop을 거치므로 절대값은 서버 환경과 다르다. 전후 비교로만 본다.
- **반복 횟수**: 대부분 3회 측정이다. 통계적 유의성 검정이나 워밍업 통제는 하지 않았고, 3회가 거의 같은 항목(상품 조회)과 흩어진 항목(선착순 burst의 연결 실패 수)을 구분해서 읽어야 한다.
- **데이터 규모**: 상품 2,000개, 주문 10만 건이다. 상품 조회는 DB가 이미 빨라서 캐시 효과가 작게 나왔고, 규모가 커지면 달라질 수 있다.
- **선착순 응답 시간**: 선점은 DB 부하(트랜잭션 수)를 줄였지만 이 규모에서 p95는 바뀌지 않았다. 이득이 응답 속도가 아니라 DB 부하라는 점을 같이 읽어야 한다.
- **정산 기준 측정**: 하루 정산이 늘다 줄던 원인은 확인하지 못했다(DB 통계 영향으로 추정).
- **배포 환경(EC2) 재측정은 하지 않았다**: t3.small(2GB, 버스트 CPU)에 앱, DB, Redis, Prometheus, Grafana가 같이 있고, 측정 PC에서 인터넷을 거쳐야 해서 로컬과 비교가 안 된다. 대신 대시보드(Prometheus, Grafana)로 배포 환경의 메모리와 지표를 확인했고(서버 메모리 여유와 지표 수집 정상), 같은 시나리오의 재측정은 환경 비교가 아니라 서버 용량 확인 목적이라 별도 과제로 둔다.
